# GSB-26：文本分块与截断缺陷修复

纯 Python 3 标准库实现，无第三方依赖。

## 文件结构

- `src/chunker_buggy.py` — 有缺陷的原始实现（保留用于回归对比）
- `src/chunker.py` — 修复后的实现
- `tests/test_chunker.py` — 复现用例 + 内容守恒断言 + 策略测试
- `benchmark.py` — 修复前后长文本耗时对比

## 四类现网问题与复现

`tests/test_chunker.py` 中的 `BuggyReproductionTests` 稳定复现：

1. **变音符号被切成两半**：`"cafe" + U+0301` 按 4 码位切片后，
   第二个片段以孤立组合记号开头。
2. **表情序列被拆成孤立码位**：`"ok👍🏽!"` 按 3 码位切片后，
   肤色修饰符 🏽 与 👍 分离。
3. **零宽连接符残留在片段末尾**：`"a👨‍👩b"` 按 3 码位切片后，
   首片段以 ZWJ (U+200D) 结尾。
4. **截断后无法还原原文**：按 UTF-8 字节预算截断 `"ab中文cd"`，
   切口落在"中"的字节中间产生 U+FFFD，`head + text[len(head):] != text`。

## 修复方案

先按字素簇（grapheme cluster）分段，再只在簇边界处切分/截断，
因此任何片段都不会以不完整字素结尾，且各片段顺序拼接逐字符等于原文
（`ConservationTests` 对全部样例 × 全部策略 × 多种步长做守恒断言）。

### 字素边界判定依据（UAX #29 实用子集，基于 unicodedata）

- **Extend 不断开**（GB9）：组合记号（`unicodedata.combining != 0`
  或类别 Mn/Mc/Me）、肤色修饰符 U+1F3FB–U+1F3FF、
  变体选择符 FE00–FE0F / E0100–E01EF 与前字符合并。
- **ZWJ 前后均不断开**（GB9/GB11 的保守合并）：ZWJ 序列
  （如 👨‍👩‍👧）整体为一簇，片段末尾不会残留孤立 ZWJ。
- **Regional Indicator 两两配对**（GB12/GB13）：国旗不被拆散。
- **退化输入**：文本以不完整序列开头（如首字符是组合记号）时，
  该字符自成一个簇；以 ZWJ 结尾时并入前一个簇。两种输入均被覆盖。

## 两种（实际三种）截断策略

由调用方通过 `strategy=` 选择，截断点永远是字素边界：

- `codepoints`：按字素簇数量限制。适合"按字符数配额"的场景，
  与渲染宽度无关。与旧实现并存但绝不拆簇。
- `width`：按显示宽度限制（East Asian Width：W/F 计 2，组合记号、
  控制/格式符计 0，其余计 1；含 ZWJ 的簇整体按一个显示单元计 2）。
  肤色修饰符（U+1F3FB–U+1F3FF）等 Extend 并入基字符、不额外占宽：
  `👍` 与 `🏽` 在 East Asian Width 中同为 W，朴素求和会把 `👍🏽`
  算成 4 列，按字素簇口径只计 2 列，与终端实际渲染一致。
  适合终端列宽、定宽预览。同一簇永不拆分，实际宽度可能略小于
  limit 但绝不超出（截断路径）。例：`"中文ab"` limit=3 时，width 策略得 `"中"`，
  codepoints 策略得 `"中文a"`。
- `bytes`：按 UTF-8 字节预算限制，修复第 4 类问题，
  截断结果与原文剩余部分可直接拼接还原。

### 分块路径的超宽簇例外（显式声明并测到）

`chunk_text` 保证每个片段不超过 `size`，**唯一例外**：单个字素簇自身的
代价就超过 `size`（如 `strategy="width", size=1` 时遇到宽度 2 的汉字，
或 `strategy="bytes", size=3` 时遇到占 4 字节的 😀）。字素簇不可拆分，
拆分必然破坏"片段不以不完整字素结尾"与拼接守恒两条保证，因此该簇独占
一个片段且该片段超出预算；除此以外所有片段均满足预算，且全部片段顺序
拼接仍逐字符等于原文。`truncate` 没有此例外——放不进预算的超宽簇直接
丢弃，结果对任何 limit 都严格不超预算。

## 耗时对比（python3 benchmark.py，本机实测）

| 码位数 | 缺陷版(码位) | 修复版(字素) | 修复版(宽度) | 修复版(字节) |
|---|---|---|---|---|
| 50,000 | 0.02 ms | 11.0 ms | 20.7 ms | 12.3 ms |
| 200,000 | 0.09 ms | 44.2 ms | 83.1 ms | 49.1 ms |
| 800,000 | 1.88 ms | 179.2 ms | 333.5 ms | 198.9 ms |

均为线性复杂度。额外开销来源：

- 缺陷版只做一次 `range` 切片，几乎是纯内存拷贝；
- 修复版需逐码位调用 `unicodedata.combining/category` 做边界判定
  （字素策略的主要开销）；
- 宽度策略额外做 `east_asian_width` 查询与簇宽度累加（约再翻倍）；
- 字节策略额外做每簇 UTF-8 编码长度计算。

80 万码位约 0.18–0.33 秒，对分页/预览场景可接受；如需更高性能，
可对 `unicodedata` 查询结果做缓存或预编译区间表。
