## 稳定遍历顺序规则（默认配置，实际输出严格按此执行）

配置默认：`Graph(directed, order=OrderPolicy.SORTED, duplicate_policy="multigraph")`。

1. **邻接表显式排序**：建图后 `freeze()`（`walk` 时若未冻结会自动冻结，幂等）
   对每个节点的邻接边按全序键 **`(目标节点键, 边 id 键)` 升序**排序。
   因此遍历顺序只取决于 (图, 配置)，**与 `add_edge` 录入先后无关**——打乱录入
   顺序后节点序 / 边序的 SHA-256 完全相同（见下文实测）。
2. **序键**：默认 `default_order_key(x) = (类型名, x)`。同为 int（bool 归入 int）
   按数值、同为 str 按字典序；跨类型按类型名分段，杜绝 `3 < "a"` 的 TypeError；
   不可比对象再用 `id()` 兜底，保证是全序。可传 `order_key=` 自定义。
   - `OrderPolicy.SORTED`（默认）：按上述规则排序。
   - `OrderPolicy.INSERTION`：保留 `add_edge` 录入顺序（旧行为，不排序）。
3. **节点序（先序 DFS + 发现即标记 / gray-marking）**：
   - 单源：起点最先访问；处理边 (u,v) 时若 v 未发现则立即深入 v，v 的全部邻接边
     先于 u 的后续邻接边处理，回溯后再继续；每个节点最多入栈一次。
   - 全图：`walk(None)` / `walk_all()` 按“节点键升序”依次选源，覆盖所有
     （含不连通）分量；分量内部同上。
4. **边序**：每条逻辑边在**第一次被看到**时触发一次 `on_edge`，触发先后即边序。

顺序逐条核对：`python3 verify.py` 会打印 4 种（有向/无向 × multigraph/simple）
图的邻接表、节点序、边序，并与独立参照逐元素比对。

## 重复边与自环去重策略（`duplicate_policy`）

- **`"multigraph"`（默认，不去重）**：边以 **edge_id 为唯一身份**。
  - 相同 (u,v) 的并行边只要 edge_id 不同就各保留、各触发一次；邻接表内按
    `(目标键, edge_id 键)` 稳定排序。
  - edge_id 不允许重复录入，违反直接抛 `ValueError`（避免“同 id 两条边”这种
    语义歧义）。
- **`"simple"`（折叠为简单图）**：同一节点对只保留 edge_id 键最小的一条。
  - 有向按有序对 (u,v) 折叠；无向按无序对 {u,v} 折叠（端点先按键规范化为 lo,hi）。
  - 自环 (u,u) 同样按 (u,u)/{u} 折叠，最多一条。
- **自环**：永远只在 u 的邻接表存 **1 份**（无向也不镜像复制），最多看到 1 次。
- **无向普通边**：两端邻接表各存 1 份镜像，遍历时按 edge_id 去重，每条逻辑边
  恰好 1 次；有向边只存 1 份，不建去重集合（千万边省数百 MB）。

## 可复现性（同图同配置 → 完全一致）

- 同一图同配置连跑多次、以及**打乱 `add_edge` 录入顺序后重建**，节点序与边序的
  规范化 SHA-256 必须相同；实测在十万 / 百万 / 千万规模上均 `identical=true`。
- 哈希是**流式**计算（`verify.streaming_walk_hashes` 边遍历边更新），不保存
  节点 / 边序列，千万规模也几乎不额外占内存。

## 性能与内存实测

环境：Python 3.12.3，Linux，16 核 x86_64，15 GiB 内存。图为有向图，主干
`i→i+1` 保证从 0 全可达 + LCG 确定性随机边，`seed=20260928`。遍历用回调计数、
不保存序列（`track_nodes/edges=False`）；计时为预热 2 轮后 3 轮中位数，RSS 取自
`/proc/self/statm`，遍历峰值由 10 ms 采样线程测得。

**1,000,000 节点 / 10,000,000 边（有向 multigraph，SORTED）**

| 指标 | 实测值 |
| --- | --- |
| 建图耗时 | 28.0 s |
| freeze（邻接表排序）耗时 | 22.0 s |
| 遍历耗时（中位数） | 8.77 s（8.69 / 8.77 / 8.90 s） |
| 遍历吞吐 | ~1.14M 边/秒 |
| 图占用 RSS | 3260 MB |
| 遍历额外峰值 RSS | +80 MB（visited 集合 + 显式栈） |
| 遍历结束残留增量 | ≈ 0 MB（状态在 finally 释放） |
| 访问节点 / 处理边 | 1,000,000 / 10,000,000，`completed=true` |
| 节点序 SHA-256 | `7b8f269a…0b878b` |
| 边序 SHA-256 | `93b0d31a…f4cc27` |
| 打乱录入后哈希 | 节点序、边序均一致（`identical=true`） |

**100,000 节点 / 1,000,000 边**：建图 1.32 s，freeze 1.90 s，遍历 0.435 s
（~2.30M 边/秒），图占 329 MB，遍历额外峰值 +3.1 MB；与独立参照实现
**逐元素相等**（节点 100,000、边 1,000,000），打乱录入后两哈希一致。

**100,000 节点纯链**：建图 0.09 s，freeze 0.16 s，遍历 0.041 s；节点序严格
`0..99999`、边序 `0..99998`（`order_strictly_increasing=true`），与参照逐元素一致。

说明：以上为 CPython 解释执行、每条边执行一次 Python 回调的口径。内存大头是图
本身（每边 `Edge` namedtuple + 双份邻接槽位 + edge_id 集合）；`freeze` 排序为
一次性成本（Timsort 边 id 键算完即释放，不长留千万级对象），遍历算法自身在
百万节点 / 千万边下额外峰值仅约 80 MB。完整 JSON 见 `results/benchmark.json`。
