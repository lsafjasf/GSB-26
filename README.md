# 分块并行矩阵乘法（Node.js，仅标准库）

行主序 `Float64Array` + `SharedArrayBuffer` 存储，`worker_threads` 真多线程并行，
分块大小与线程数均可配置。串行与并行共用同一个内层 kernel，结果**逐位一致**。

## 运行命令

```bash
node test.js           # 串并行一致性 + 特殊形状 + 自动配置自测（49 项断言）
node bench_block.js    # 块大小 vs 耗时曲线（默认 1024^3，8 线程）
node bench_threads.js  # 线程数 vs 加速比（默认 1024^3, bs=64）
node bench_auto.js     # 自动配置 vs 手工配置在多形状下的耗时对比
taskset -c 0-3 node bench_threads.js   # 受限 4 核下的加速比
```

库用法：

```js
const { createMatrix, matmulSerialBlocked, ParallelMultiplier } = require('./matmul');
const A = createMatrix(1000, 777, (i, j) => Math.random());
const B = createMatrix(777, 999, (i, j) => Math.random());
const C = createMatrix(1000, 999);
matmulSerialBlocked(A, B, C, 64);            // 串行分块
const pool = new ParallelMultiplier(8);      // 线程池可复用
await pool.multiply(A, B, C, 64);            // 并行分块，结果与串行逐位相同
await pool.close();

// 自动配置（推荐）：按形状 + 机器核数 + 缓存自动推导块大小与线程数
const { matmulAuto, recommendConfig, closeAutoPools } = require('./matmul');
await matmulAuto(A, B, C);                                    // 全自动
await matmulAuto(A, B, C, { blockSize: 32, numThreads: 4 });  // 手工覆盖（可单独给一项）
console.log(recommendConfig(1000, 777, 999));                 // 查看推荐值与逐条推导依据
await closeAutoPools();                                       // 退出前关闭缓存的线程池
```

## 自动配置（recommendConfig / matmulAuto）

`recommendConfig(m, k, n)` 按矩阵形状、机器核数与缓存容量推导
`{ blockSize, numThreads }`，并返回 `reasons`：每条推导都带具体数字，
同一台机器、同一形状结果**可复算**。机器参数通过
`/sys/devices/system/cpu` 探测（物理核按 topology 的 core_id 去重，
缓存读 cpu0 的 L1d/L2/L3），非 Linux 平台回退到保守默认值。

推导规则（常量见 `matmul.js` 顶部）：

1. **块大小看 L2**：A/B/C 三块 `bs²` 工作集（`3·bs²·8B`）不超过 L2 的 1/4，
   取不超过该上界的最大 2 的幂，夹在 `[16, 256]`。
   本机 L2=1MB → `bs≤√(1MB/96B)=104` → **bs=64**，与 `bench_block.js`
   实测甜点（64~128）一致；留 3/4 余量给 B 行流式加载与系统其它数据。
2. **线程数看物理核与工作量**：上限为物理核数（SMT 逻辑核实测边际收益低，
   且受限核数下超额订阅会回落）；`flops=2mkn < 1e7` 时 worker 调度开销
   大于收益，直接单线程；否则每 `1e7` flop 增配一个线程。
3. **负载均衡看瓦片数**：C 瓦片数不足 `2×线程数` 时块减半（下限 16），
   线程数再以瓦片数为上限（瓦片是调度最小单位，多出的线程只会空转）。

手工覆盖入口：`matmulAuto(A, B, C, { blockSize, numThreads })` 或
`recommendConfig(m, k, n, { ... })`，覆盖项跳过对应推导，其余仍自动。

### 自动 vs 手工实测（`bench_auto.js`，Ryzen 7 9700X，取多次最小值）

| 形状 | 自动推荐 | 自动 ms | 手工 bs=64,t=8 | 手工 bs=128,t=16 |
|------|---------|--------:|---------------:|-----------------:|
| 极小 3x3x3 | bs=64, t=1 | 0.001 | 0.205 | 0.307 |
| 极小 32³ | bs=64, t=1 | 0.020 | 0.213 | 0.300 |
| 极扁 4x8192x4 | bs=64, t=1 | 0.146 | 0.217 | 0.301 |
| 极扁 2048x4x2048 | bs=64, t=4 | 5.71 | 4.78 | 3.64 |
| 极扁 4096x2x4096 | bs=64, t=7 | 23.3 | 22.6 | 23.1 |
| 非方阵 1000x777x999 | bs=64, t=8 | 87.1 | 88.2 | 73.3 |
| 非方阵 1536x256x768 | bs=64, t=8 | 33.1 | 35.1 | 31.2 |
| 方阵 512³ | bs=64, t=8 | 15.2 | 14.8 | 14.9 |
| 方阵 1024³ | bs=64, t=8 | 135.0 | 138.1 | 107.3 |

结论：

- **极小/极扁（flops < 1e7）**：自动判为单线程，比手工开 8~16 线程快
  2~200 倍——worker 调度固定开销约 0.2~0.4ms，小矩阵上完全盖过计算本身。
- **中等工作量**：按 `1e7 flop/线程` 增配，与手工最优差 20% 以内。
- **大矩阵**：自动（物理核 8 线程）与手工默认持平；手工开到 16 逻辑核
  可再快约 10~20%（SMT 榨取剩余吞吐），但在受限核数（taskset）或共享
  机器上超额订阅会回落，故自动策略保守取物理核，需要时可用
  `{ numThreads: os.cpus().length }` 手工覆盖。
- 所有形状下自动结果与串行分块**逐位相等**（`max|diff|=0`，见
  `test.js` 自动配置断言组）。

## 设计要点

- **分块**：C 划分为 `bs×bs` 瓦片，k 维同样按 `bs` 分段；边界瓦片用 `min()` 截断，
  天然支持非整块尺寸、bs=1、bs 大于矩阵、0 行/列等退化形状。
- **缓存友好**：内层 kernel 用 i-k-j 循环序，`a[i][k]` 提升为标量，B 行与 C 行均连续访问；
  `a[i][k]===0` 时跳过整行（零矩阵快路径）。
- **并行**：每个 C 瓦片只被一个 worker 拥有（无数据竞争、无需锁），worker 用
  `Atomics.add` 从共享计数器动态领取瓦片，自动负载均衡，适配不规则形状。
- **确定性**：每个瓦片内部按固定 kk 顺序累加，与串行路径的累加顺序完全一致，
  因此并行结果与串行分块结果**逐位相等**（测试中用容差 0 断言）。

## 一致性测试与误差分析

`test.js` 覆盖：1x1、块大于矩阵、非整块（127x131x113、bs=1）、极扁（2x400x3）、
极长（400x2x400）、行向量点积、外积、零矩阵、0 行矩阵、单位矩阵、512³、
1000x777x999 不规则大矩阵、单线程池、非法维度抛 `RangeError`。全部 28 项通过。

两级断言：

1. **并行 vs 串行分块**：`max|diff| = 0`（逐位相等）。两条路径对每个 C 元素的
   浮点累加顺序完全相同，不存在调度相关的舍入差异。
2. **分块 vs 朴素参照**：容差 `tol = 8·k·ε·max|A|·max|B|`（ε=2⁻⁵²≈2.2e-16）。
   浮点加法不满足结合律，一旦实现改变求和顺序（如分块、并行归约），每个元素
   的舍入误差上界约为 `k·ε·max|a||b|`（k 次累加，每次相对误差 ≤ε），取 8 倍余量。
   本实现中分块恰好保持了与朴素相同的累加顺序，实测 diff 全为 0；
   容差断言是为允许替换成会重排求和顺序的 kernel（如 SIMD 分pairwise 求和）而设。

## 实测数据（AMD Ryzen 7 9700X，8 物理核 / 16 逻辑核，Node 18，1024³，取 3~5 次最小值）

### 块大小 vs 耗时（`bench_block.js`）

| blockSize | 串行分块 | 并行 8 线程 | 并行加速比 |
|----------:|---------:|------------:|-----------:|
|         8 |  885 ms  |     324 ms  |      2.73x |
|        16 |  803 ms  |     212 ms  |      3.80x |
|        32 |  711 ms  |     161 ms  |      4.41x |
|    **64** |  **640 ms** | **130 ms** |  **4.91x** |
|       128 |  634 ms  |     132 ms  |      4.81x |
|       256 |  719 ms  |     146 ms  |      4.93x |
| 朴素 ijk  | 1961 ms  |      —      |       —    |

取舍依据：块太小（≤16）时循环开销与 B 行重复加载占比高；块太大（≥256）时
`bs×bs` 的 A、B 块（256²×8B=512KB/块）超出 L2（1MB/核）容纳能力，缓存命中率下降。
64~128 是甜点：三块 `bs²` 工作集（64²×8B×3≈96KB）可驻留 L1/L2，瓦片数量
（1024/64）²=256 也足够 16 个线程均衡调度。默认取 **bs=64**。
分块本身即使串行也比朴素快约 3 倍（缓存局部性），并行再叠加约 5 倍。

### 线程数 vs 加速比（`bench_threads.js`，bs=64）

| 线程数 | 16 核可用 | 受限 4 核（taskset） |
|-------:|----------:|---------------------:|
|      1 | 0.95x     | 0.92x                |
|      2 | 1.48x     | 1.39x                |
|      4 | 2.95x     | 2.42x                |
|      8 | 4.22x     | 2.30x（超售，回落）   |
|     12 | 4.84x     | 2.85x                |
|     16 | 5.12x     | 2.57x                |

达不到线性加速的原因：

- **SMT 不是真核**：16 逻辑核 = 8 物理核 × 2 超线程，同核两个线程共享执行端口
  与 L1/L2，8 线程之后只能挤 SMT 的剩余吞吐，故 8→16 线程仅 4.2x→5.1x。
- **单核睿频抬高基线**：串行基线跑在单核 boost 频率上，多核满载时全核频率更低。
- **内存带宽共享**：kernel 是 load/store 密集型（标量 JS 无 SIMD），多核竞争
  L3 与内存带宽。
- **调度与同步开销**：瓦片领取（Atomics）、worker 消息往返、V8 堆外开销，
  线程数 1 时的 0.95x 即这部分固定成本。
- 受限 4 核时，线程数超过物理核后加速比停滞甚至回落（8 线程 2.30x < 4 线程
  2.42x），说明**线程数不应超过可用物理核数**，超售只会增加上下文切换。

## 内存上界

- 数据：`8·(m·k + k·n + m·n)` 字节，A/B/C 各一份 `SharedArrayBuffer`，
  所有 worker 共享同一份内存，**不为任何分块复制输入**。
- 额外开销：瓦片任务表 `O((m/bs)·(n/bs))` 个四元组、一个 4 字节共享计数器、
  每个 worker 约 8~10MB 的 V8  isolate 常驻内存。计算过程不分配与矩阵规模
  相关的临时缓冲（直接累加进 C，瓦片独占无冲突）。
- 实测：4096³（数据 384MB）8 线程峰值 RSS 515MB ≈ 数据 + 8 个 worker 固定开销，
  与上界公式吻合；若逐块拷贝输入，RSS 会随线程数线性膨胀数 GB。
